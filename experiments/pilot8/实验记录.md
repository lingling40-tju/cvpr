# ActiveVLN 语义事件奖励：第一版小规模实验

日期：2026-09-30。状态：代码已部署、两组各完成 2 个优化 step；这是训练链路与奖励信号实验，尚无未见场景性能结论。

## 实现

- 云端隔离工作树：`/Knowin/foundation/haozhiwang/whz/ActiveVLN_semantic_20260930`，分支 `codex/semantic-reward-20260930`；基础提交 `3a0c63b00e4f42c828cc74c3554afce17641da60`。原工作树及端口 5001 服务未改。
- 指令解析：先用 Qwen3-VL-2B 和后来使用的 Qwen3-VL-8B 生成事件候选；加事件动词与目标词校验。2B 曾把“走上台阶”错标为“下楼”，因此训练使用人工复核的 8 条 episode、17 个事件清单，而非直接信任自动解析。
- 核验：冻结的 [Qwen3-VL-8B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct)，本地下载修订 `0c351dd01ed87e9c1b53cbc748cba10e6187ff3b`，独立推理环境 `transformers==4.57.6`。输入当前事件、动作前后 RGB、实际执行动作与仿真器位移，返回 `Y/N/U`。`cross/enter/pass` 要求实际向前移动；`descend` 要求高度下降；`stop_near` 要求真实 `STOP`。`U` 不给分。
- 状态机：按顺序确认，每个事件只给一次；整条轨迹的语义分上限为 1。成功另加固定 2 分下界，两组使用相同设置，保证到达目标优先于最多 1 分的过程奖励。
- 奖励接入：实验服务在端口 5002；`VLNCEService` 创建包装后的环境，逐轮奖励进入 `env_reward`。当前 GRPO 仍将轨迹分数求和，**尚未实现动作级信用分配**。每轮最多 3 个动作，因此事件记录的时间精度也是一轮。

核心代码在本目录的 `vlnce_server/semantic_reward/`；训练配置与原文件的对应改动在 `overrides/`。云端运行脚本与同名本地脚本在 `scripts/`。

## 实验配置

两组都从同一个 `Qwen2.5-VL-3B_sft_r2r_envdrop_multiturn` SFT 权重开始。训练集是相同的 8 条 R2R train episode；每组 2 个 optimizer step，batch 4，每条采样 2 条 rollout，共 16 条。两组均从 episode 起点开始，不使用专家动作前缀。对照组语义权重为 0，实验组语义奖励预算为 1。两组终点奖励、固定成功下界、训练卡、仿真器、数据与其余超参数相同。

先执行 `bash tools/start_semantic_services.sh` 启动 5002/5003 服务，再执行 `bash tools/run_semantic_pilot.sh control` 和 `bash tools/run_semantic_pilot.sh event`。两组训练脚本应串行运行；已存在的健康服务会由启动脚本复用。真实 stdout、rollout JSONL、TensorBoard 文件及汇总 JSON 已复制到本目录 `results/`。

## 回放检查

8 条专家动作轨迹在仿真器中均到达目标。事件核验结果：4 条完成全部事件，2 条完成一部分，2 条未获得过程分；总计确认 11/17 个清单事件。浴室 episode 2889 中，“看见水槽但还在门外”的前两轮判 `U`，进入浴室后的第三轮才确认 `enter`，最后 `STOP` 时确认 `stop_near`。本目录 `replay_2889/frame_02.jpg`、`frame_03.jpg`、`frame_04.jpg` 保存了对应真实 RGB。楼梯与办公室正例见 `replay_2298/`、`replay_2412/`。原地转向再提前 `STOP` 的负例获得 0 语义分。

**质量限制：** `U` 较多；episode 8033 在浅台阶的单轮高度变化不足门槛而完全漏判；episode 10440 的地标始终未被确认。上述回放不是独立人工标注的验证集，不能据此宣称判定器准确率。后续必须增加正负例人工标注，尤其检查“看见门但未穿过”和“穿过错误门”。

## 两组实际训练结果

| 指标 | 对照组 | 事件组 |
| --- | ---: | ---: |
| optimizer step | 2 | 2 |
| rollout | 16 | 16 |
| 到达目标 | 13/16 | 13/16 |
| 平均整条轨迹奖励 | 9.325 | 10.455 |
| 平均事件进度 / 语义分 | 0 | 0.656 |
| 事件确认次数 | 0 | 23 |
| 事件判定为不确定的轮次 | 0 | 33 |
| 判定服务错误 | 0 | 0 |

第一步的 8 条 rollout 在两组中**动作序列完全相同**；逐条比较时，事件组总奖励相对对照组恰好增加该轨迹的语义分。例如 episode 7110 的一条失败轨迹在对照组得 0 分，在事件组因完成“下楼”得 0.5 分。训练日志的 `NaiveRewardManager` 读到了变化后的 `env_reward`，两组均完成反向传播并保存 `global_step_2` 权重。因此，过程奖励确实进入了训练链路。

两组训练 rollout 成功数相同；平均奖励增加主要是奖励定义改变，**不能解释为导航能力提升**。第二步的轨迹已受不同权重影响，不能像第一步那样逐条作因果配对。这次没有跑 R2R val-unseen，也没有多随机种子。
